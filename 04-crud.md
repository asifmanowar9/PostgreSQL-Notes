# 03 - Data Manipulation Language (DML)

DML is used for inserting, reading, updating, and deleting data (often called CRUD operations).

## The `RETURNING` Clause

One of PostgreSQL's most powerful and frequently used features is the `RETURNING` clause. It allows you to retrieve data that was just modified by an `INSERT`, `UPDATE`, or `DELETE` statement, all in a single query.

This is especially useful for getting auto-generated values (like IDs or default timestamps) immediately after creating a record.

### Example: Inserting Data

```sql
INSERT INTO posts (title, content)
VALUES
  ('My First Post', 'This is the first post content.'),
  ('My Second Post', 'This is the second post content.')
RETURNING *;
```

## UPSERT (`ON CONFLICT`)

In many applications, you want to insert a row, but if a row with that unique identifier already exists, you want to update it instead of crashing. PostgreSQL handles this gracefully with the `ON CONFLICT` clause.

_Note: The column you check for conflict MUST have a UNIQUE constraint (like a Primary Key)._

```sql
INSERT INTO posts (id, title, content)
OVERRIDING SYSTEM VALUE
VALUES (4, 'My Updated Title', 'My updated content.')
ON CONFLICT (id)
DO UPDATE SET
    title = EXCLUDED.title,
    content = EXCLUDED.content
RETURNING *;
```

### Key Learnings from this Query:

1. **`ON CONFLICT (id) DO UPDATE SET...`**: If ID 4 already exists, do not fail. Instead, update the row.
2. **`EXCLUDED`**: A special PostgreSQL keyword that refers to the data you were _attempting_ to insert (e.g., `EXCLUDED.title` refers to 'My Updated Title').
3. **`OVERRIDING SYSTEM VALUE`**: Because we defined our `id` column as `GENERATED ALWAYS AS IDENTITY`, PostgreSQL strictly prevents us from manually inserting an ID to protect the internal counter. We must explicitly use this keyword to bypass that protection. (If we had used `GENERATED BY DEFAULT AS IDENTITY`, this wouldn't be required, but it is less safe).
